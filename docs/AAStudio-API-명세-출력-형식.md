# AAStudio API 명세 출력 형식

## 1. 목적

AAStudio가 API 명세를 어떤 형식으로 보여주고 저장할지 정의한다.

이 명세는 문서용에 그치지 않고, 실제 백엔드에 요청을 보내 호출 테스트를 수행할 수 있어야 한다.
또한 소스코드 기준 자동 동기화와 수동 추가를 함께 지원해야 한다.

## 2. 기본 원칙

- 사람이 읽기 쉬워야 한다.
- OpenAPI로 내보낼 수 있어야 한다.
- 요청/응답 예제가 보여야 한다.
- 코드 흐름에서 추정한 항목임을 표시할 수 있어야 한다.
- 실제 B/E 호출 테스트를 수행할 수 있어야 한다.
- 공통 인증 정보를 지정할 수 있어야 한다.
- 소스코드 동기화 결과와 수동 추가 항목을 구분할 수 있어야 한다.

## 3. 필수 항목

- API 그룹
- HTTP method
- path
- summary
- auth required
- request schema
- response schema
- status code
- error code
- example request
- example response
- test request
- test response
- test result

## 4. 출력 형태

### 4.1 화면 표시

- 카드 형태 목록
- 상세 패널
- 요청/응답 예제 토글
- JSON 보기

### 4.2 파일 출력

- OpenAPI JSON
- OpenAPI YAML
- Markdown 문서

### 4.3 테스트 실행

- 실제 백엔드 URL로 호출
- 공통 인증 헤더/토큰 적용
- 샘플 데이터 기반 테스트 가능
- 요청/응답 비교
- 실행 결과 저장

### 4.4 동기화 및 수동관리

- 소스코드에서 API를 자동 추출한다.
- 수동으로 API를 추가할 수 있다.
- 자동 동기화 결과와 수동 등록 항목을 함께 비교할 수 있다.
- 변경 이력과 충돌 여부를 표시한다.

## 5. 추론 표시

- 코드에서 확인된 항목
- 로컬 LLM이 추정한 항목
- 사용자가 확정한 항목
- 실제 테스트로 검증한 항목
- 자동 동기화된 항목
- 수동 추가된 항목

## 6. 검토 기준

- 경로가 실제 라우트와 맞는지
- 인증 여부가 맞는지
- 요청/응답 스키마가 충분한지
- 상태 코드가 적절한지
- 실제 호출 결과와 문서가 일치하는지
- 동기화된 항목과 수동 항목이 구분되는지

## 7. 공통 인증

- 프로젝트별 공통 인증 방식을 지정할 수 있어야 한다.
- Bearer token, API key, Basic auth, Cookie session 등으로 확장 가능해야 한다.
- 테스트 실행 시 공통 인증은 기본값으로 자동 적용될 수 있어야 한다.

## 8. 샘플 데이터

- API 테스트는 DB에 유지되는 샘플 데이터를 사용할 수 있어야 한다.
- 샘플 데이터는 프로젝트 단위로 보존된다.
- 샘플 데이터는 재사용 가능해야 한다.

## 9. 다음 단계

이 형식을 기준으로 API 명세 탭의 실제 출력 레이아웃을 고정하면 된다.
