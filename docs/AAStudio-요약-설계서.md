# AAStudio 요약 설계서

## 1. 목적

AAStudio는 `my_harness`를 레퍼런스로 삼아, 개인 PC 전용 폐쇄망 환경에서 동작하는 로컬 분석 워크벤치다.

핵심 목적은 소스 코드를 분석해 DB 모델링, 다이어그램, API 명세, Wiki, WBS, 리뷰, 파일 관리를 한 곳에서 다루는 것이다.
AAStudio는 하나의 프로그램 안에서 여러 프로젝트를 생성하고 전환하며 관리할 수 있어야 한다.

## 2. 핵심 원칙

- 로컬 PC에서만 동작한다.
- 로컬 LLM을 사용한다.
- 외부 공개는 readonly로만 허용한다.
- 파일 다운로드는 허용하되 수정과 업로드는 막는다.
- 상세 취약점 점검은 전용 솔루션이 담당하고, AAStudio는 코드 흐름 기반 분석과 리뷰 보조를 맡는다.

## 3. 기능 범위

- 로그인 및 사용자 인증
- 프로젝트 관리
- 사용자 관리
- 코드 그룹 관리
- 다중 프로젝트 관리
- 소스 코드 스캔
- 소스코드 점검
- 표준단어사전 점검
- 보안점검 항목 검토
- DB 모델링
- 다이어그램 생성
- API 명세 작성
- API 소스코드 동기화 및 수동관리
- 실제 백엔드 호출 테스트
- 공통 인증 프로필 관리
- 샘플 데이터 유지
- Wiki 작성과 버전 이력
- 파일 업로드와 다운로드
- WBS 등록과 계층 관리
- 각 단계별 최종 산출물 생성
- 프로젝트별 대시보드에서 단계별 담당자 정보 표시

## 4. 분석 방식

### 4.1 소스코드 점검

PMD, SonarQube류의 규칙과 정책을 분석 기준으로 삼는다.

로컬 LLM은 이를 바탕으로 코드 스멜, 구조적 문제, 위험 패턴, 리뷰 포인트를 추정한다.

### 4.2 보안점검 항목

AAStudio는 아래 같은 코드 흐름 기반 보안 점검을 보조한다.

- SQL 인젝션
- XSS
- SSRF
- 인증/권한 검증 누락
- 파일 업로드/다운로드 취약 패턴
- 세션 관리 문제
- 정보 누출
- 평문 전송

### 4.3 역할 구분

- 전용 보안 솔루션: 상세 취약점 진단
- AAStudio: 코드 기준 분석, 리뷰 보조, 후보 이슈 정리

### 4.4 단계별 산출물

AAStudio는 각 단계가 끝날 때 다음과 같은 최종 산출물을 만든다.

- 소스 스캔 요약
- 소스코드 점검 리포트
- 표준단어사전 점검 리포트
- 표준단어사전 점검 엑셀
- 보안점검 후보 리포트
- DB 모델 설계서
- ERD 산출물
- API 명세서
- API 테스트 리포트
- Wiki 버전 문서
- WBS 구조 문서

### 4.5 프로젝트 관리

AAStudio의 모든 분석과 문서는 프로젝트 단위로 분리된다.

- 프로젝트 생성
- 프로젝트 열기
- 프로젝트 전환
- 최근 프로젝트 목록
- 프로젝트 복사
- 프로젝트 삭제

### 4.6 프로젝트 대시보드

프로젝트별 대시보드는 다음 정보를 보여준다.

- 현재 단계
- 담당자명
- 직급
- 담당자 연락처
- 담당자 이메일
- 관련 업무
- 관련 산출물
- 최근 변경 내역

### 4.7 프로젝트 대시보드 정책 반영

프로젝트별 대시보드는 다음을 포함한다.

- 현재 단계
- 단계 상태
- 담당자명
- 직급
- 담당자 연락처

### 4.8 단계별 담당자 배정

프로젝트의 각 개발 단계에는 담당자 정보를 연결한다.

- 담당자명
- 직급

프로젝트별 대시보드는 운영 정보를 요약해서 보여주고, 단계별 담당자와 상태를 보여준다.

- 프로젝트명

- 단계 상태
- 담당자명
- 직급
- 연락처
- 이메일
- 관련 업무
- 관련 산출물
- 최근 변경 내역

## 5. UI 구성

- 로그인 화면과 업무 화면을 분리한다.
- 로그인 후 상단 공통 네비게이션을 제공한다.
- 좌측: 프로젝트, 최근 목록, Wiki, WBS, 파일, 검색
- 중앙: 프로젝트 대시보드, 프로젝트 관리, 사용자 관리, 코드 그룹 관리, DB 모델링, 다이어그램, API 명세, API 테스트, 소스코드 점검, 보안점검, Wiki, WBS 탭
- 우측: 선택 항목 속성 패널
- 상단: 프로젝트, 사용자, 코드 그룹, 로그아웃
- 공통: 카드형 대시보드, 탭 기반 작업, 좌측 탐색, 중앙 작업, 우측 속성의 3단 구조를 유지한다.

### 5.1 참조 컴포넌트 패턴

- DB 모델링은 테이블 카드, 컬럼 폼, 캔버스, 공유 뷰어 구조를 따른다.
- 다이어그램은 플로우 캔버스, 툴바, 편집 엣지, 공유 뷰어 구조를 따른다.
- Wiki는 사이드바, 메인 편집기, 뷰어 구조를 따른다.
- API는 그룹 목록, endpoint 카드/에디터, 테스트 결과 뷰어 구조를 따른다.
- 네 화면 모두 목록 또는 트리, 중앙 편집 영역, 전역 액션의 공통 축을 유지한다.

## 6. 저장 방식

- 메타데이터는 SQLite로 저장한다.
- 첨부 파일은 파일 시스템에 저장한다.
- Wiki 저장 시 버전 이력을 생성한다.
- 메타데이터 저장은 단일 데이터소스를 기준으로 설계한다.

## 7. 공유 방식

- 내부에서는 전체 기능을 사용한다.
- 외부 공유는 readonly로만 제공한다.
- 외부 사용자는 문서와 다이어그램을 보고 파일을 다운로드할 수 있다.

1. 로드맵과 요약 설계서의 범위를 먼저 고정한다.
2. 저장 구조와 핵심 화면 구성을 다음 문서에서 분리해 정의한다.
3. SQLite 테이블 초안으로 문서 간 공통 메타데이터를 정리한다.
4. 분석 흐름도와 단계별 산출물 정책으로 실행 순서를 묶는다.

## 10. 1차 확인 기준

- 로컬 PC 전용이라는 제약이 문서 전체에서 유지되어야 한다.
- 프로젝트 단위 분리가 모든 기능 설명에 일관되게 반영되어야 한다.
- 외부 공유는 readonly라는 정책이 유지되어야 한다.
- 다음 문서들이 이어질 수 있도록 입력과 출력의 경계가 보여야 한다.
