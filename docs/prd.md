# AAStudio 제품 요구사항 정의서(PRD)

## 1. 문서 개요

- 제품명: AAStudio
- 제품 유형: 시스템 아키텍처 관리 도구
- 문서 상태: 초안
- 작성일: 2026-09-22

## 2. 제품 목표

AAStudio는 시스템 개발에 필요한 아키텍처 정보를 한 곳에서 작성하고 연결하는 협업 도구다. 다이어그램, 데이터베이스 모델, API 명세, 기술 문서를 각각 별도 도구로 관리하지 않고 프로젝트 단위로 통합한다.

핵심 목표는 다음과 같다.

1. 개발자가 시스템 구조를 빠르게 시각화할 수 있어야 한다.
2. DDL과 API payload 같은 기존 산출물을 붙여 넣어 문서 작성 시간을 줄여야 한다.
3. 아키텍처 결정과 구현 지식을 WIKI로 축적하고 검색할 수 있어야 한다.
4. 다이어그램·DB·API·문서가 서로 연결되어 변경 영향을 추적할 수 있어야 한다.

## 3. 대상 사용자

- 시스템 아키텍트: 서비스 구조, 데이터 흐름, 배포 구성을 설계한다.
- 백엔드 개발자: DB 스키마와 API 계약을 작성·검토한다.
- 프론트엔드 개발자: API payload와 응답 구조를 확인한다.
- 기술 리더/리뷰어: 설계 결정과 변경 이력을 검토한다.
- 프로젝트 구성원: WIKI에서 개발 지식을 공유한다.

## 4. 제품 범위

### 포함 범위

- 프로젝트/공간 단위 아키텍처 자산 관리
- 시스템 다이어그램 편집
- DB 모델링 및 DDL 기반 자동 생성
- API 정의서 및 payload 기반 명세 생성
- Confluence와 유사한 WIKI형 문서 관리
- 자산 간 링크와 검색
- 변경 이력 및 협업 기능의 기반 구조

### 초기 제외 범위

- 실제 서버 배포 및 운영 모니터링
- DB에 대한 직접적인 변경 실행
- API 호출을 통한 운영 데이터 수정
- 완전한 실시간 공동 편집
- 외부 문서 도구로의 양방향 동기화

## 5. 정보 구조

프로젝트를 최상위 단위로 두고 다음 공간을 제공한다.

```text
프로젝트
├─ Dashboard
├─ Diagram
├─ DB Modeling
├─ API Specification
├─ WIKI
└─ Settings
```

각 자산은 프로젝트에 속하며, 다이어그램 노드·DB 테이블·API 엔드포인트·WIKI 문서 사이에 참조 링크를 설정할 수 있다.

## 6. 기능 요구사항

## 6.1 다이어그램

### 현재 개발된 내역

현재 화면은 아키텍처 작업 공간 형태로 구현되어 있으며, 좌측에 Spaces 탐색 영역, 중앙에 캔버스, 우측에 선택 객체 속성 패널을 제공한다.

- 프로젝트 공간 및 다이어그램 목록 탐색
- 선택/이동 도구
- 서비스 노드, 이미지 블록, 그룹 박스, 텍스트 상자 생성
- 사각형, 둥근 사각형, 타원, 원, 삼각형, 마름모, 오각형, 육각형, 팔각형, 별, 하트, 번개, 구름, 문서, 말풍선, 데이터베이스 등 도형 생성
- 노드 간 연결선 생성 및 편집
- 연결선의 꺾임/곡선, 시작·끝 화살표, 색상, 굵기, 점선, 애니메이션 설정
- 연결선 라벨/배지 설정
- 노드 다중 선택, 복사, 붙여넣기, 삭제, 키보드 방향키 이동
- 노드 크기 조절 및 회전
- 그룹 박스와 그룹 내부 노드 관리
- 확대/축소
- 텍스트 상자의 글자색, 글꼴, 글자 크기 설정
- 텍스트 상자·서비스 노드·도형의 배지 설정
- 노드의 채우기 색상, 테두리 색상, 선 굵기, 선 스타일, 투명도 설정
- 아이콘 라이브러리에서 Material Symbols/Remix Icon 선택
- 아이콘 검색, 기본·AWS·GCP·Azure·인프라·모델링 카테고리 및 서비스 그룹 필터
- 아이콘 위치와 색상 모드 설정

### 목표 요구사항

- 다이어그램 자동 저장 및 수동 저장
- 다이어그램 버전 및 변경 이력 관리
- PNG/SVG/PDF 내보내기
- 노드와 DB 테이블/API/WIKI 문서 간 링크
- 정렬, 간격 맞춤, 그룹화, 잠금 기능
- 다이어그램 템플릿 및 자주 사용하는 노드 저장
- 검색 결과에서 관련 노드 위치로 이동
- 권한에 따른 보기/편집/관리자 역할 지원

### 주요 사용자 흐름

1. 프로젝트에서 다이어그램을 선택한다.
2. 서비스·DB·외부 시스템을 노드로 배치한다.
3. 연결선과 라벨을 추가해 데이터 흐름을 표현한다.
4. 노드 속성 패널에서 텍스트, 배지, 도형, 아이콘을 설정한다.
5. 관련 DB/API/WIKI 자산을 연결한다.
6. 저장하고 내보내거나 리뷰 링크를 공유한다.

## 6.2 DB 모델링

### 목적

데이터베이스 구조를 코드와 다이어그램으로 함께 관리하고, 기존 DDL을 재활용해 모델 작성 시간을 줄인다.

### 요구사항

- VS Code와 유사한 편집기 경험
- SQL 구문 강조, 줄 번호, 검색, 자동 들여쓰기
- DDL 붙여넣기 또는 파일 입력
- `CREATE TABLE`, 컬럼, PK, FK, 인덱스, 코멘트 파싱
- DDL 분석 결과로 ERD 자동 생성
- 테이블 이동, 확대/축소, 관계선 확인
- 테이블명/컬럼명/자료형/NULL 여부/기본값/코멘트 표시
- 파싱 오류 위치와 원인 표시
- ERD 수정 사항을 DDL 또는 모델 정보로 다시 확인
- 데이터베이스 방언별 확장 가능 구조(MySQL/MariaDB, PostgreSQL 등)
- DB 모델과 다이어그램 노드 연결
- 모델 및 DDL 버전 관리

### 입력 예시

사용자는 다음과 같은 DDL을 편집기에 붙여 넣고 `ERD 생성`을 실행한다.

```sql
CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL,
    status VARCHAR(30) NOT NULL,
    CONSTRAINT fk_orders_user
        FOREIGN KEY (user_id) REFERENCES users(id)
);
```

## 6.3 API 정의서

### 목적

API 요청/응답 payload를 기반으로 엔드포인트 명세를 빠르게 만들고, 개발·검토·공유에 사용할 수 있도록 한다.

### 요구사항

- API 목록 및 폴더 구조 관리
- HTTP 메서드, 경로, 설명, 인증 방식 관리
- 요청 헤더, path/query parameter, request body 정의
- response status별 payload 정의
- JSON payload 붙여넣기 및 필드 자동 추출
- 중첩 객체와 배열 구조 지원
- 필드명, 자료형, 필수 여부, 설명, 예시값 관리
- JSON Schema 또는 OpenAPI 형식으로 가져오기/내보내기
- 예시 요청/응답과 코드 스니펫 제공
- API와 다이어그램 노드·WIKI 문서 연결
- 변경 이력과 리뷰 상태 관리

### payload 처리 흐름

1. 사용자가 요청 또는 응답 JSON을 붙여 넣는다.
2. 시스템이 객체·배열·필드·자료형을 분석한다.
3. 사용자가 필수 여부와 설명을 보완한다.
4. API 정의서와 예시 payload를 저장한다.
5. 필요 시 OpenAPI 문서로 내보낸다.

## 6.4 WIKI

### 목적

Confluence와 유사한 게시판형 문서 공간을 제공해 아키텍처 결정, 운영 규칙, 개발 가이드를 프로젝트 지식으로 축적한다.

### 요구사항

- 스페이스/폴더/문서 계층 구조
- 문서 생성, 편집, 이동, 보관, 삭제
- 제목, 본문, 작성자, 작성일, 수정일, 태그 관리
- Markdown 또는 블록 기반 편집기
- 제목, 목록, 표, 코드 블록, 인용, 이미지, 링크 지원
- 다이어그램·DB·API 자산 임베드 또는 링크
- 문서 검색 및 태그 필터
- 즐겨찾기와 최근 문서
- 문서 버전 및 변경 이력
- 댓글과 멘션
- 공개/비공개 및 프로젝트 권한
- 문서 템플릿 제공

### 권장 문서 템플릿

- 아키텍처 결정 기록(ADR)
- 시스템 개요
- 서비스 운영 가이드
- 장애 대응 절차
- API 사용 가이드
- 데이터 모델 설명
- 배포 및 환경 설정

## 7. 공통 요구사항

### 프로젝트와 권한

- 프로젝트를 생성하고 구성원을 초대할 수 있어야 한다.
- 보기, 편집, 리뷰, 관리자 권한을 구분한다.
- 모든 자산은 프로젝트 범위 안에서 접근 권한을 적용한다.

### 검색

- 다이어그램, 테이블, API, WIKI를 통합 검색한다.
- 제목, 식별자, 태그, 본문, 컬럼명, 엔드포인트를 검색 대상에 포함한다.
- 검색 결과에서 자산 유형과 프로젝트를 필터링한다.

### 저장과 이력

- 사용자의 변경 내용을 자동 저장한다.
- 수동 저장 시점에 버전을 생성할 수 있다.
- 자산별 생성자, 수정자, 수정일을 기록한다.
- 삭제된 자산은 일정 기간 복구할 수 있어야 한다.

### UI/UX 원칙

- 고정 사이드바와 유동 작업 영역을 사용한다.
- 기술 정보는 JetBrains Mono 등 고정폭 글꼴을 사용한다.
- 다이어그램은 캔버스 중심, DB/API는 코드·데이터 중심, WIKI는 문서 중심으로 제공한다.
- 단축키와 키보드 접근성을 지원한다.
- 장시간 작업을 고려해 밀도 높은 정보와 명확한 선택 상태를 제공한다.

## 8. 비기능 요구사항

- 지원 환경: 최신 Chrome, Edge, Firefox, Safari
- 반응형: 데스크톱 우선, 태블릿 대응, 모바일 기본 조회 지원

- 확장성: DB 방언, API 포맷, 아이콘 세트를 플러그인 구조로 확장
- 데이터 교환: JSON, SQL, OpenAPI, Markdown 기반 내보내기 지원

## 12. 하네스 기반 아키텍처 및 개발 방식

AAStudio는 `D:\ai\my_harness`를 기준 하네스로 사용한다. 하네스는 제품 런타임 기능이 아니라, 요구사항 분석부터 설계·구현·검증·작업 이력 관리까지의 개발 운영 구조를 정의한다.

### 12.1 프로젝트 구조

```text
AAStudio/
├─ AGENTS.md                    # 프로젝트 진입 규칙과 개발 하네스 규칙
├─ docs/
│  ├─ prd.md                    # 제품 요구사항
│  └─ working_history/          # 작업별 결정·검증·다음 단계
├─ src/main/                    # 제품 구현
├─ src/test/                    # 자동화 테스트
├─ .agents/                     # Codex용 프로젝트 스킬/보조 규칙(필요 시)
└─ .codex/                      # Codex 에이전트 정의(필요 시)
```

하네스 원본의 공통 규칙과 도구는 `D:\ai\my_harness`에서 관리하고, AAStudio에만 필요한 규칙은 프로젝트의 `AGENTS.md`와 `docs/`에 둔다. 하네스 원본 파일을 제품 코드와 무분별하게 복제하지 않는다.

### 12.2 표준 작업 단계

| 단계 | 목적 | 주요 산출물 |
|---|---|---|
| Context | 기존 코드·문서·테스트·실행 환경 확인 | 조사 결과, 영향 범위 |
| Plan | 요구사항과 수용 기준 확정 | 작업 계획, 테스트 시나리오 |
| Design | 모듈·데이터·에이전트 경계 설계 | 설계 문서, 결정 사항 |
| Implement | 최소 범위 기능 구현 | 코드, 단위/통합 테스트 |
| Verify | QA·회귀·정적 검증 | 테스트 결과, 실패 원인 |
| Record | 작업 결과와 다음 단계 기록 | `docs/working_history/` 문서 |

### 12.3 에이전트 역할

- Analyst: 요구사항, 현재 구현, 영향 범위를 분석한다.
- Architect: 제품 모듈과 데이터 흐름을 설계한다.
- Builder: 코드와 테스트를 구현한다.
- QA: 수용 기준과 회귀 시나리오를 검증한다.
- Reviewer: 보안, 성능, 유지보수성, 설계 일관성을 검토한다.

작업 크기가 작으면 하나의 에이전트가 여러 역할을 수행할 수 있지만, 분석·구현·검증 결과는 분리해서 기록한다.

### 12.4 품질 게이트

- 코드 변경은 가능한 경우 Red-Green-Refactor 순서를 따른다.
- 구현 전 수용 기준을 먼저 작성한다.
- 기능 테스트와 회귀 테스트를 구분한다.
- 테스트 실행이 불가능하면 환경 제약과 대체 검증 방법을 기록한다.
- 완료 보고에는 변경 파일, 검증 명령, 결과, 미해결 이슈를 포함한다.

### 12.5 작업 이력 규칙

기능 단위 작업이 끝나면 `docs/working_history/`에 다음 내용을 기록한다.

- 작업 목적과 관련 PRD 항목
- 조사한 기존 구현과 영향 범위
- 선택한 설계와 선택하지 않은 대안
- 변경 파일과 주요 변경 내용
- 실행한 테스트/검증과 결과
- 남은 리스크 및 다음 작업

이 구조를 통해 다이어그램, DB 모델링, API 정의서, WIKI 기능이 각각 독립적으로 개발되면서도 동일한 하네스 규칙과 품질 기준을 공유하도록 한다.
