# AAStudio 로컬 Wiki/리뷰/WBS 워크벤치 설계서

## 1. 문서 목적

이 문서는 `my_harness`를 기준 레퍼런스로 삼아, `AAStudio`에서 정리하는 로컬 분석 워크벤치의 설계를 정리한다.

목표는 다음과 같다.

- 소스 코드를 로컬에서 분석하여 DB 모델링, 다이어그램, API 명세 초안을 자동 생성한다.
- 생성 결과를 Wiki, 리뷰, 파일 첨부, WBS와 연결해 하나의 작업 허브로 관리한다.
- 소스코드 점검 기능에서 PMD, SonarQube류의 규칙과 정책을 분석 기준으로 삼는다.
- 상세 취약점 점검은 전용 솔루션이 담당하고, 여기서는 코드 흐름 기준의 분석과 리뷰 보조를 제공한다.
- 외부 허용 시에는 읽기 전용으로만 공개하고, 파일 다운로드만 허용한다.
- 구현은 아직 하지 않고, 제품/시스템 설계만 확정한다.

## 2. 제품 개요

### 2.1 제품 성격

이 제품은 설치형 Python 애플리케이션이다. 실행 후 로컬 PC 내부에서 로컬 모델을 구동하고, 분석 결과를 동일 PC 안의 웹 UI 또는 데스크톱 UI에서 확인한다.

### 2.2 핵심 가치

- 수동 입력 부담을 줄인다.
- 소스 분석 결과를 자동 초안으로 만든다.
- DB 모델링, ERD, API 명세, Wiki, WBS를 한 프로젝트 안에서 연결한다.
- 로컬 전용이므로 민감한 소스의 외부 반출을 최소화한다.

## 3. 범위

### 3.1 포함 범위

- 프로젝트 생성/열기/저장
- 소스 폴더 스캔
- 로컬 코드 모델 기반 분석
- 소스코드 점검
- 보안점검 항목 점검
- DB 모델 초안 생성
- 다이어그램 초안 생성
- API 명세 초안 생성
- Wiki 문서 작성 및 버전 이력
- 파일 드래그 앤 드롭 업로드
- WBS 업무 등록 및 계층 관리
- 외부 readonly 공개 모드
- 파일 다운로드 허용

### 3.2 제외 범위

- 대규모 클라우드 동기화
- 다중 사용자 실시간 편집
- 개인 PC를 외부 공개 서버로 운영하는 방식
- 업무 할당, 일정, 리소스 최적화 같은 고도화된 PM 기능

## 4. 사용 시나리오

### 4.1 기본 시나리오

1. 사용자가 프로젝트를 연다.
2. 소스 코드 폴더를 지정한다.
3. 로컬 모델이 파일을 분석한다.
4. 소스코드 점검 결과와 보안점검 결과가 먼저 생성된다.
5. DB 모델링, 다이어그램, API 명세 초안이 생성된다.
6. 사용자가 결과를 Wiki에 정리하고 WBS 항목에 연결한다.
7. 필요한 파일을 업로드한다.
8. 저장 시 Wiki 버전 이력이 생성된다.

### 4.2 외부 공유 시나리오

1. 내부 사용자가 특정 프로젝트를 readonly로 공개한다.
2. 외부 사용자는 웹 UI에서 문서와 다이어그램을 열람한다.
3. 외부 사용자는 첨부 파일을 다운로드할 수 있다.
4. 외부 사용자는 수정, 업로드, 삭제를 할 수 없다.

## 5. 아키텍처 원칙

### 5.1 로컬 우선

- 분석 엔진은 사용자 PC에서만 구동한다.
- 모델도 로컬 PC에서만 실행한다.
- 원본 소스는 기본적으로 로컬에 머문다.

### 5.2 폐쇄망 우선

- 인터넷 연결 없이도 동작해야 한다.
- 외부 연동은 필수 기능이 아니다.
- 배포와 운영은 단일 PC 기준으로 설계한다.

### 5.3 공유는 제한적으로

- 외부 공개는 readonly로만 허용한다.
- 파일은 다운로드 가능하되, 업로드와 수정은 막는다.
- 필요 시 IP 제한이나 토큰 기반 접근을 추가한다.

### 5.4 초안과 확정 분리

- 로컬 모델은 정답 생성기가 아니라 초안 생성기다.
- 사용자가 검토 후 확정한다.
- 확정된 결과만 프로젝트 산출물로 저장한다.

## 6. 기능 설계

### 6.1 소스 분석

- 프로젝트 폴더 스캔
- 언어/프레임워크 추정
- 엔티티, DTO, 라우트, SQL, ORM 코드 추출
- PMD, SonarQube류의 규칙과 정책을 로컬 모델의 분석 기준으로 전달
- 결과를 구조화 JSON으로 저장

### 6.2 소스코드 점검

- PMD, SonarQube류의 규칙과 정책을 분석 기준으로 사용
- 로컬 LLM이 소스를 읽고 정책 위반 가능성을 판단
- 코드 스멜, 버그 가능성, 구조적 품질 문제 탐지
- 중복 코드, 미사용 코드, 위험한 API 사용 탐지
- 규칙 기반 결과와 모델 추론 결과를 함께 표시
- 파일/라인 단위로 근거를 남겨 리뷰가 가능하게 함

### 6.3 보안점검 항목

- 코드 인젝션
- SQL 인젝션
- 디렉토리 인덱싱
- 에러 페이지 미적용
- 정보 누출
- XSS
- SSRF
- 약한 비밀번호 정책
- 불충분한 인증 절차
- 불충분한 권한 검증
- 취약한 비밀번호 복구 절차
- 프로세스 검증 누락
- 악성 파일 업로드
- 파일 다운로드 취약점
- 불충분한 세션 관리
- 데이터 평문 전송
- 쿠키 변조
- 관리자 페이지 노출
- 자동화 공격
- 불필요한 method 악용
- 상세 취약점은 전용 보안 솔루션 결과를 연동하거나 수동 검토한다.

### 6.4 DB 모델링

- 테이블 생성/수정/삭제
- 컬럼 정의
- PK/FK/Unique/Index 정의
- 관계 추론 및 편집
- DDL 생성용 초안 저장

### 6.5 다이어그램

- ERD 자동 생성
- 노드/엣지 편집
- 자동 정렬
- 확대/축소/이동
- PNG/SVG/PDF 내보내기

### 6.6 API 명세

- endpoint, method, path 추출
- request/response 스키마 추출
- status code, error code, auth 여부 추정
- OpenAPI 초안 생성
- 문서 미리보기 제공

### 6.7 Wiki

- 페이지 생성/수정/삭제
- 저장 시 버전 이력 생성
- 이전 버전 복원
- 페이지 간 링크
- 태그/검색
- 마크다운 또는 리치 텍스트 편집

### 6.8 파일 업로드

- Wiki 편집 화면에 드래그 앤 드롭 업로드
- 첨부 목록 관리
- 이미지 미리보기
- 파일 링크 자동 삽입
- 다운로드 경로 관리

### 6.9 WBS

- 업무 등록
- 상하위 구조 관리
- 산출물 연결
- 이력 기록
- 담당자 할당과 일정 관리는 후순위로 미룸

## 7. UI 구성

### 7.1 메인 구성

- 좌측: 프로젝트, Wiki, WBS, 파일 탐색
- 중앙: 탭 영역
  - DB 모델링
  - 다이어그램
  - API 명세
  - 소스코드 점검
  - 보안점검
  - Wiki
  - WBS
- 우측: 속성 패널
- 상단: 분석, 저장, 내보내기, 공유, 검색

### 7.2 탭별 UX

- DB 모델링 탭은 스키마 편집 중심
- 다이어그램 탭은 시각화 중심
- API 명세 탭은 OpenAPI 검토 중심
- 소스코드 점검 탭은 PMD/SonarQube류의 규칙 기반 분석 중심
- 보안점검 탭은 코드 흐름 기반 점검과 보조 검토 중심
- Wiki 탭은 문서화와 이력 중심
- WBS 탭은 업무 분해와 링크 중심

## 8. 권한 모델

### 8.1 Owner

- 전체 권한
- 생성/수정/삭제/업로드/공개 가능

### 8.2 Readonly User

- 조회 가능
- 파일 다운로드 가능
- 수정, 업로드, 삭제 불가

### 8.3 Guest

- 제한된 열람만 가능
- 다운로드 여부는 별도 설정 가능

## 9. 저장소 설계

### 9.1 SQLite 사용 이유

- 설치가 간단하다.
- 파일 단위 백업이 쉽다.
- 로컬 전용 메타데이터 저장에 적합하다.
- 프로젝트별 단일 파일 또는 소수 파일로 관리할 수 있다.

### 9.2 저장 데이터

- 프로젝트 메타데이터
- 소스 분석 결과
- 소스코드 점검 결과
- 보안점검 결과
- DB 모델 정의
- 다이어그램 정의
- API 명세
- Wiki 페이지 및 버전
- 파일 첨부 메타데이터
- WBS 구조
- 접근 로그

### 9.3 파일 저장 원칙

- 첨부파일 원본은 파일 시스템에 저장한다.
- SQLite에는 경로, 파일명, 해시, 크기, 생성 시각만 저장한다.
- 대용량 바이너리를 DB에 직접 넣는 방식은 기본안으로 두지 않는다.

## 10. 로컬 모델 설계

### 10.1 모델 실행 조건

- 사용자 PC 내부에서만 실행
- CPU-only 기준 동작 가능
- i7 / RAM 32GB 기준을 전제로 설계

### 10.2 모델 선택 방향

- 기본 모델은 3B급 양자화 모델
- 옵션으로 7B급 모델을 둘 수 있음
- 모델은 초안 생성용이며, 검토는 사람이 수행

### 10.3 분석 방식

- 파일 단위 분석
- 정적 분석 우선
- 로컬 모델은 정적 분석 결과를 보완
- 장문 코드는 청크 단위로 분할 처리

## 11. 외부 readonly 공유

### 11.1 목표

- 개인 PC 내부 작업은 유지한다.
- 필요한 경우 외부 사용자는 읽기만 가능하도록 한다.
- 파일은 다운로드만 허용한다.

### 11.2 허용/차단

- 허용: 문서 보기, 다이어그램 보기, API 명세 보기, 파일 다운로드
- 차단: 수정, 업로드, 삭제, 실행 설정 변경

### 11.3 보안 원칙

- 외부 공개는 명시적으로 켠 경우에만 허용
- 세션 토큰 또는 비밀번호 사용
- IP 제한 가능
- 접근 로그 저장

## 14. 리스크와 대응

### 14.1 모델 정확도

- 리스크: 모델이 DB 관계나 API 스펙을 잘못 추정할 수 있다.
- 대응: 초안 생성으로 한정하고, 근거 파일과 신뢰도 표시를 제공한다.

### 14.2 UI 복잡도

- 리스크: Wiki, WBS, 파일, 명세가 한 화면에 몰리면 복잡해진다.
- 대응: 탭 분리와 속성 패널을 유지한다.

### 14.3 저장소 복잡도

- 리스크: 파일과 버전 이력이 커질 수 있다.
- 대응: SQLite는 메타데이터에 집중하고 파일은 파일 시스템에 둔다.

### 14.4 외부 공유 보안

- 리스크: readonly 공개가 잘못 설정되면 수정이 유입될 수 있다.
- 대응: 읽기 전용 경로와 쓰기 경로를 명확히 분리한다.

## 15. 결론

이 설계는 개인 PC 전용, 폐쇄망, 로컬 모델 구동이라는 조건에 맞는 구조다.

핵심은 다음 네 가지다.

- 로컬에서 분석한다.
- SQLite와 파일 시스템으로 저장한다.
- Wiki, WBS, 리뷰, 파일을 한 프로젝트 안에 묶는다.
- 소스코드 점검과 코드 기준 보안점검을 분리해 제공한다.
- 외부 공개는 readonly와 다운로드로만 제한한다.

이 구조라면, 개인 PC를 서버처럼 과도하게 운용하지 않으면서도 문서화와 리뷰 협업이 가능한 실용적인 워크벤치를 만들 수 있다.
